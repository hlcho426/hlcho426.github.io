AI가 게임을 실행하는 데 성공했어도, 요청한 규칙을 구현했는지는 따로 확인해야 한다. SWE-Game은 기획 요구를 실제 실행 상태와 연결해 검사하는 연구다. 9월 공개된 자료를 다시 읽고, 작은 게임 기능의 검증에 가져올 방법을 정리한다.

## 무슨 일이 있었나
{:.briefing-heading}

### 질문 — 실행되는 게임은 기획한 게임과 같은가

연구진은 Godot 기준 게임 41개에서 247개 과제를 구성했다. 짧은 요청으로 제작, 상세 기획서 구현, 미완성 프로젝트 완성, 버그 수정, Godot에서 Unity로 이식하는 다섯 유형이다. 코드가 실행되는지뿐 아니라 의도한 기능과 진행을 지키는지 평가한다.

### 방법 — 행동과 상태를 연결해 검사한다

공통 계측 인터페이스가 플레이어·위험물 같은 역할을 엔진의 오브젝트와 연결한다. 평가자가 소유한 검사와 입력 재생으로 위치·접촉·상태 변화를 관찰하고, 입력하지 않는 대조 실행도 비교한다. 화면은 별도 시각 평가로 살핀다.

### 결과 — 최고 점수와 검사 정확도의 의미

여섯 모델과 각 개발 프레임워크를 평가했다. 짧은 요청 제작의 최고 총점은 50.38/100, 상세 기획서 구현은 59.68/100이다. 두 과제는 입력과 채점 기준이 달라, 차이를 기획서 하나의 인과 효과로 읽으면 안 된다.

사람이 판정한 100개 생성 게임의 1,200개 검사항목에서는 실행 검사와 영상 기반 모델 판정의 균형 정확도가 각각 92.59%, 약 78.41%였다. 균형 정확도는 정상 수용률과 결함 탐지율의 평균이며, 게임 제작 성공률이 아니다.

### 한계 — 모델만의 순위나 재미 점수가 아니다

프로젝트 41개와 특정 모델·프레임워크 조합의 결과다. 대형 프로젝트와 장기 개발의 범위는 제한적이고, 자동 점수를 플레이어 경험과 연결하는 평가도 더 필요하다. arXiv 프리프린트의 보고 결과이며 이 글에서 재현하지 않았다.

## 왜 중요한가
{:.briefing-heading}

**분석:** 제작 요청에 결과 화면만 적으면, 그 화면까지 가는 규칙이 빠져도 발견하기 어렵다. 기능과 그 기능을 확인할 행동을 같이 적는 방식이 중요하다.

### 구체적인 작업 예시 — 체크포인트와 재시작

**필자가 만든 설명용 예시다.** 플랫폼 게임에서 ‘체크포인트를 지나면 죽은 뒤 그 위치에서 다시 시작한다’를 시험한다고 하자.

| 입력 | 확인할 상태 | 실패로 기록할 것 |
|---|---|---|
| 체크포인트 통과 후 낙사 | 저장된 위치와 재시작 위치 | 시작 지점으로 돌아감 |
| 체크포인트를 지나지 않고 낙사 | 최초 시작 위치 | 지나지 않은 지점에서 시작 |
| 아무 입력 없이 대기 | 진행과 위치 | 자동으로 클리어됨 |

이 표는 연구의 실행 결과가 아니라 검사 설계의 예시다. 먼저 기대 상태를 정하고, 그 뒤 구현을 검사해야 구현된 동작을 정답으로 되풀이하는 일을 줄일 수 있다.

### 어떤 개발자에게 관련 있나 · 지금 도입할 만한가

**필자의 판단:** AI에게 구현·수정을 맡기거나 기존 규칙을 보존해야 하는 개발자에게 관련 있다. 벤치마크 전체 설치보다 작은 기능에 행동·상태·대조 조건을 붙이는 방법부터 적용할 만하다. 조작감과 재미는 사람의 플레이 검증을 별도로 남긴다.

## 개발에 적용할 점
{:.briefing-heading}

- 구현 전에 성공·실패·무입력 조건을 적고 기대 상태를 기록한다.

- 수정 전후 같은 입력을 실행해 고친 기능과 기존 기능을 함께 검사한다.

- 영상으로만 확인한 항목과 실행 상태로 확인한 항목을 나눠 기록한다.
