게임 개발에서 오류 로그를 분류하는 일과 여러 시스템을 고치는 일은 필요한 판단의 범위가 다르다. Claude Haiku 5.5의 발표를 계기로 반복 작업에 모델을 나눠 쓰는 방식을 살펴본다. 먼저 공식 비교의 조건을 정리하고, 로그 분류와 문서 검색을 예로 무엇을 맡기고 어떻게 결과를 검사할지 설명한다.

## 무슨 일이 있었나
{:.briefing-heading}

### 반복 작업과 복잡한 작업의 역할 구분

10월 7일 발표는 요약·분류·데이터 조회 같은 작업을 Haiku의 용도로 제시한다. 조절 가능한 effort 설정도 소개한다. 같은 글은 복잡한 에이전트 코딩에는 Sonnet과 Opus가 더 적합하다고 설명한다. 작은 모델로 모든 업무를 대체한다는 발표는 아니다.

### 공급사의 평가와 현장 성과는 다르다

발표에는 벤치마크와 고객 설명이 함께 실렸다. 이는 공급사가 공개한 자료이며 이 글에서 재현한 결과가 아니다. 특히 평균 비용 절감 주장은 요청 길이와 토큰 사용량의 가정이 포함되므로, 자기 작업의 비용이나 속도로 그대로 옮겨 계산하지 않는다.

공식 표의 Terminal-Bench 4.0은 명령줄에서 복잡한 여러 단계의 작업을 처리하는 능력을 평가한다. 발표에 실린 수치는 Haiku 5.5 **39.2%**, 비교용 Sonnet 5.5 **70.6%**다. 이는 Unity 게임의 완성률이나 오류 로그 분류 정확도가 아니다. 공급사도 복잡한 에이전트 코딩에는 더 큰 모델을 권한다. 작은 모델의 용도와 큰 모델의 용도를 구분해서 읽어야 한다.

### 제작 작업은 어떻게 달라지나

**필자의 적용 해석:** 일을 맡길 때 ‘오류를 고쳐 줘’만 요청하면 원인 조사·수정·검증이 한 작업에 묶인다. 반대로 정답과 범위를 명시할 수 있는 앞단 작업을 분리하면, 그 부분의 결과부터 확인할 수 있다.

예를 들어 로그를 받아 종류별로 정리하는 단계, 관련 문서의 구절을 찾는 단계, 실제 코드를 수정하는 단계를 나눈다. 작은 모델을 앞의 두 단계에 시험하고 수정은 기존 검토 절차에 남기는 구성이다. 이 방법이 실제로 더 빠르거나 저렴한지는 같은 작업 표본으로 비교해야 한다. 작업을 나누는 데 드는 시간도 포함한다.

### 구체적인 작업 예시

**아래는 설명용 작업 설계이며, Haiku를 실행해 얻은 결과가 아니다.** 입력을 제한하고 결과를 검사할 수 있는 작업부터 시작하는 예시다.

| 작업 | 제공할 입력 | 기대할 결과 | 실패로 기록할 조건 |
|---|---|---|---|
| 오류 로그 분류 | 비공개 정보가 없는 시험 로그와 허용된 분류 목록 | 각 로그의 분류와 근거가 된 문장 | 원인 추측을 확정하거나 목록 밖 분류를 만듦 |
| 문서 검색 | 공개 API 문서 몇 개와 질문 하나 | 관련 구절과 문서 위치, 없으면 ‘찾지 못함’ | 문서에 없는 함수를 답하거나 다른 버전 내용을 섞음 |
| 대사 데이터 정리 | 가상 대사 행과 필수 열 규칙 | 누락된 ID·태그·빈 행 목록 | 대사 의미를 임의로 바꾸거나 정상 행을 삭제함 |

로그 분류라면 허용 분류를 ‘컴파일 오류 / 실행 중 예외 / 경고 / 판단 불가’로 먼저 정해 보자. 컴파일러가 오류라고 표시한 시험 로그에는 ‘컴파일 오류’와 해당 근거를 기대할 수 있다. 단서가 부족한 경우에는 ‘판단 불가’를 허용한다. 모델이 결론을 내놓았다는 이유만으로 원인이 확정된 것은 아니다.

문서 검색은 더 명확하게 검사할 수 있다. 답에 적힌 함수가 제공한 문서에 있는지, 지목한 구절이 질문에 답하는지 사람이 확인한다. 잘 읽히는 답과 근거가 맞는 답을 따로 기록하는 것이다.

### 실제 사용 조건

공식 글은 Claude Platform과 AWS·Google Cloud·Azure에서의 제공을 안내한다. API 가격표는 입력 길이에 따라 구분된다. 각 플랫폼의 계정·지역·계약·한도는 별도로 확인해야 하며 여기서는 검증하지 않았다.

발표 시점 가격표에서 입력 길이 100,000토큰 이하의 API 단가는 입력 100만 토큰당 **$0.10**, 출력은 **$0.50**다. 100,000토큰을 넘으면 각각 **$0.50**, **$2.50**로 달라진다. 토큰은 모델이 텍스트를 처리하는 단위이며, 짧은 분류 요청과 긴 문서 요청을 같은 단가로 계산하면 안 된다. 이 표는 API 단가로, 일반 채팅 구독의 이용 조건을 뜻하지 않는다.

### 확인된 범위와 한계

요약·분류에 적합하다는 설명과 비용·성능 비교는 회사 발표다. 직접 사용이나 생산성 측정은 하지 않았다. 데이터 보관·라이선스·세부 접근 조건도 이 발표만으로 확정하지 않는다.

## 왜 중요한가
{:.briefing-heading}

**분석:** 모델 선택은 작업별 정답과 실패 기준을 먼저 세우면 비교하기 쉬워진다. 분류 오류를 사람이 빨리 발견할 수 있는 업무와, 여러 단계의 판단을 연결해야 하는 업무는 검토 비용이 다르다. 호출 단가를 줄였어도 수정 시간이 늘면 전체 생산성이 개선됐다고 보기 어렵다. 그래서 도입 기준에는 모델이 성공한 작업뿐 아니라 틀린 결과를 누가 언제 발견하는지도 포함해야 한다. 위험한 결정을 자동 실행하기 전에 검증 단계를 두는 것은 모델의 설명과 별개의 운영 선택이다.

### 어떤 개발자에게 관련 있나

**필자의 판단:** 같은 형식의 로그·문서·데이터를 자주 정리하고 결과를 확인할 규칙이 있는 개발자에게 관련 있다. 반면 작업량이 적거나 대부분의 시간이 설계 판단과 실제 플레이 검증에 쓰인다면, 모델을 나누는 관리 부담이 더 클 수 있다.

### 지금 도입할 만한가

**필자의 판단: 제한된 작업으로 비교할 후보.** 이미 적절한 사용 환경이 있다면 작은 표본으로 시험할 만하다. 하지만 이 발표만으로 새로운 유료 도구를 도입하거나 기존 코딩 모델을 전면 교체할 근거는 부족하다. 먼저 맡길 작업의 정답과 실패 기준이 있는지 확인한다.

## 개발에 적용할 점
{:.briefing-heading}

- 정답을 확인할 수 있는 반복 업무 표본을 준비하고 같은 입력으로 결과를 비교한다. 정확도와 처리 시간, 사람이 수정한 횟수를 함께 기록한다.

- 실패한 출력이 다음 작업으로 넘어가는 조건을 정한다. 검증이 필요한 결과는 사람이나 별도 검사 단계에서 승인한 뒤 사용한다.
