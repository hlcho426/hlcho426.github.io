> 이 글은 Unity 공식 자료와 설치된 패키지 소스를 확인해 정리한 실습 안내 초안이다. 메뉴는 Unity 6.6 계열(6000.6.0f1)의 uGUI에 포함된 TextMeshPro를 기준으로 확인했다. 버전에 따라 메뉴 위치와 표시가 조금 다를 수 있다.

## 2부. ‘미리 굽기’는 언제, 어떻게 할까?
{:.briefing-heading}
개발 중인 Dynamic 폰트는 처음 보는 글자가 나오면 그때 추가한다.<br>
**Static 폰트는 미리 준비한 글자만 사용한다.**<br>
Static 폰트는 준비된 글자를 사용하므로 해당 에셋에서 실행 중 새 글리프를 생성할 필요가 없다. 원본 폰트가 다른 곳에서 참조되지 않고 Resources 등에도 없다면 빌드에서 제외할 수 있다. 다만 아틀라스 크기와 장수에 따라 전체 용량이 달라지므로, Static이 항상 더 가볍다는 뜻은 아니다.<br>
<br>
작은 게임은 Dynamic으로도 출시할 수 있다.<br>
무조건 Static으로 바꿔야 하는 것은 아니다.<br>
글자 생성으로 인한 지연, 메모리, 빌드 크기를 실제 기기에서 확인해 결정한다.<br>
화면이 끊긴다면 먼저 Profiler로 원인을 확인한다. 새 글리프 생성이 원인일 때 Static 전환이나 필요한 문자를 로딩 중 미리 추가하는 방법 등을 비교한다. 이미지 로딩이나 UI 갱신이 원인이라면 폰트 모드만 바꿔서는 해결되지 않는다.


## 직접 해 보기

### 1. 사용할 문장을 파일에 모으기

처음에는 자동화 없이 작은 예제로 해 보자.

1. Windows 메모장을 연다.
2. 다음 문장을 넣는다.

```text
새 게임
이어하기
환경 설정
게임을 종료할까요?
예 아니요
안녕하세요! 가나다라
0123456789 ABC abc !? …
```

3. `다른 이름으로 저장`을 선택한다.
4. 파일명은 `font_characters_ko.txt`, 인코딩은 `UTF-8`로 저장한다.
5. Unity의 Project 창에서 `Assets/Fonts`로 끌어 놓는다.

이 파일에 있는 글자만 준비할 것이다. **이 예문만으로 실제 게임 전체를 커버하는 것은 아니다.** 나중에는 모든 UI·대사·아이템 설명·오류 메시지·번역을 모은 파일로 교체한다.

게임의 문장이 많아지면 대사·번역 테이블(CSV, JSON 등)에서 실제 표시할 문자열을 추출하고 중복 문자를 제거해 문자 파일을 만드는 방법을 권한다. 숫자 포맷에서 생기는 쉼표·소수점·부호·통화 기호, 날짜, 실행 중 조합되는 문장도 포함한다. 리치 텍스트 태그와 변수 이름만 수집하고 실제 출력값을 빠뜨리지 않도록 주의한다.

KS X 1001의 한글 완성형 2,350자 같은 문자 집합을 시작 자료로 사용할 수도 있다. 하지만 특정 게임의 대사를 몇 퍼센트 포함하는지 보장하는 목록은 아니다. 고유명사·신조어·의성어와 `ㅋㅋ`, `ㅠㅠ` 같은 자모는 실제 데이터로 다시 검사한다. 업데이트 때도 문자 파일을 다시 만든다.

### 2. Font Asset Creator 열기

1. 상단 `Window > TextMeshPro > Font Asset Creator`를 누른다.
2. 아래처럼 설정한다.

| 항목 | 실습 설정 |
|---|---|
| Source Font File | 처음 가져온 원본 `.ttf` |
| Sampling Point Size | Auto Sizing |
| Padding | 5 |
| Packing Method | Optimum |
| Atlas Resolution | 2048 × 2048 |
| Character Set | Characters from File |
| Character File | font_characters_ko.txt |
| Render Mode | SDFAA |

`Character File`에는 Unity Project 창의 텍스트 파일을 끌어 넣는다. `Source Font File`에는 SDF 에셋을 넣는 것이 아니다.

위 값은 소수의 문장으로 원리를 배우는 시작값이다.<br>

**여기서 Sampling Point Size는 화면의 Font Size 36과 다르다.** <br>
전자는 글자 이미지를 만들 때의 크기, 후자는 UI에서 보여 줄 크기다.<br>

**Auto Sizing과 Custom Size**<br>
Auto Sizing은 지정한 문자를 아틀라스에 넣을 수 있는 생성 크기를 찾는다. 같은 크기의 아틀라스에 문자를 더 많이 넣으면 생성 크기가 작아질 수 있다. 문자를 모두 넣었더라도 실제 화면에서 획이 충분히 구분되는지 확인한다. Custom Size는 생성 크기를 직접 정할 때 사용하며, 공간이 부족하면 일부 글자가 들어가지 못할 수 있다.

**Optimum과 Fast**<br>
Fast는 설정을 시험할 때 빠르게 배치를 계산한다. Optimum은 모든 문자를 담을 수 있는 더 큰 자동 생성 크기를 찾는 데 사용하며, 공식 문서는 최종 텍스처 생성에 이를 안내한다. 글자 윤곽끼리 빈틈없이 끼워 넣는 방식이라고 이해할 필요는 없다.

### 3. 생성하고 저장하기

1. `Generate Font Atlas`를 누른다.
2. 생성이 끝나면 미리보기와 누락 문자 보고를 확인한다.
3. `Save as...`를 누른다.
4. `Assets/Fonts` 아래에 `ui_ko_static.asset`이라는 새 이름으로 저장한다.
5. 저장한 에셋을 클릭하고 `Atlas Population Mode`가 `Static`인지 확인한다.
6. 테스트 텍스트의 `Font Asset`을 이 에셋으로 교체한다.

1부의 긴 테스트 문장을 그대로 두었다면, 이번 문자 파일에 없는 글자에서 Console 경고나 대체 문자가 나타날 수 있다. 폴백이 보완하면 네모가 보이지 않을 수도 있다. 노란색 메시지는 경고이며, 실제 문구를 읽어 어떤 문자가 어느 에셋에 없는지 확인한다.

7. 텍스트 파일에 넣었던 문장을 화면에 입력해 확인한다.

폰트를 텍스트 컴포넌트의 슬롯에 직접 연결하는 이 실습에서는 `Resources` 폴더가 필수는 아니다.
이름으로 폰트를 찾는 리치 텍스트 태그 등은 별도의 검색 경로 설정이 필요하므로 여기서는 사용하지 않는다.

글자를 미리 모아 아틀라스로 만드는 설정은 [Font Asset Creator 공식 문서](https://docs.unity3d.com/Packages/com.unity.ugui@2.0/manual/TextMeshPro/FontAssetsCreator.html)에 설명되어 있다. 메뉴 명칭 차이는 설치된 패키지를 우선 확인한다.

### 4. 누락 글자가 있다면 두 가지를 구분하기

**원본 폰트에 없는 글자**는 이미지 크기를 늘려도 생기지 않는다. 다른 폰트나 폴백이 필요하다.

**원본에는 있지만 이미지에 못 들어간 글자**라면 아틀라스 크기·Sampling Point Size·문자 분할을 검토한다. Auto Sizing으로 많은 문자를 한 장에 넣으면 개별 글자 이미지가 작아질 수 있으므로, ‘모두 들어갔다’와 ‘충분히 선명하다’를 따로 본다.


### 5. 같은 문장으로 생성 품질 비교하기

필요할 때만 별도 테스트 에셋 두 개로 해 본다. 아래 숫자는 권장값을 정하기 위한 비교 예시다.

1. 같은 원본 폰트·문자 파일·2048 아틀라스·Padding 5를 사용한다.
2. Sampling Point Size를 Custom Size로 두고 36과 72로 각각 생성해 다른 이름으로 저장한다. 누락이 생겼다면 그 수도 기록한다.
3. 같은 UI의 Font Size와 상자 크기는 유지한 채 Font Asset만 바꿔 비교한다. 작은 본문과 큰 제목에서 받침, `ㅁ`, `ㅂ`, `ㅎ`의 안쪽을 살펴본다.
4. 이번에는 생성 크기를 고정하고 Padding만 5와 10으로 바꿔 본다. 같은 외곽선 설정에서 테두리가 잘리는지, 누락 수가 바뀌는지 확인한다.

한 번에 한 조건만 바꿔야 원인을 비교하기 쉽다. 큰 값이 항상 더 좋지는 않다. 실제 표시 크기에서 품질 차이가 없는데 수용 문자 수만 줄어든다면 작은 설정을 선택할 근거가 된다. 테스트 결과를 운영 중인 에셋에 적용할 때에는 별도 갱신 절차를 거친다.

## 없는 글자를 대신 표시하는 ‘폴백’ 연결하기

폴백(Fallback)은 주 폰트에 없는 글자를 다른 폰트에서 찾는 기능이다.

이번 실습에서는 앞에서 만든 두 에셋을 연결해 볼 수 있다.

```text
ui_ko_static : 미리 준비한 글자
    ↓ 없는 글자가 있으면
처음 만든 Dynamic SDF : 원본에서 추가 시도
```

1. Project 창에서 `ui_ko_static`을 선택한다.
2. Inspector에서 `Fallback Font Assets`를 펼친다.
3. 목록의 `+`를 눌러 칸을 추가한다. 버전에 따라 Size를 늘리는 형태일 수 있다.
4. 처음 만든 **Dynamic SDF 에셋**을 넣는다.
5. 화면 텍스트에는 주 폰트인 `ui_ko_static`을 연결한다.
6. 미리 굽는 문장 파일에는 없지만 원본 폰트가 지원하는 한글을 추가해 표시되는지 확인한다.

같은 원본 폰트로 연결하면 글자 모양이 섞이는 문제를 줄일 수 있다. 원본 자체에 없는 기호는 같은 원본의 Dynamic 폴백으로도 해결되지 않는다.

> **Dynamic 폴백도 원본 폰트와 실행 중 생성 비용이 필요하다.**
> 빌드에 포함되는 Static 폰트가 Dynamic 폴백을 참조하면, 그 폴백의 원본 폰트도 필요하다. 폴백은 글자를 놓쳤을 때 유용하지만 원본 제외에 따른 용량 절약을 그대로 기대할 수는 없다. 정해진 UI·대사와 사용자 입력의 문자 범위를 나누고, 프로젝트에 필요한 구성을 선택한다.

폴백은 안전망이다. 출시 문자 검사에서 누락이 없어졌다는 뜻은 아니다. Static의 문자 포함을 검사할 때는 폴백이 보완한 것인지도 구분해야 한다. [TMP 폴백 설명](https://docs.unity3d.com/Packages/com.unity.ugui@2.0/manual/TextMeshPro/FontAssetsFallback.html)


### 폴백이 누락을 가리고 있는지 확인하기

운영 중인 에셋 대신, 위에서 만든 테스트용 Static 에셋에서 확인한다.

1. 문자 파일에 없는 글자 하나를 고른다. 예문 그대로라면 `뿅`을 후보로 쓸 수 있다. 먼저 원본 폰트가 그 글자를 지원하는지 확인한다.
2. Static 에셋의 Character Table에서 그 문자가 포함돼 있지 않은지 확인한다. 화면에 `새 게임 뿅`처럼 입력하고 표시 결과와 Console 경고를 기록한다.
3. Dynamic 폴백을 연결한 뒤 다시 확인한다. 글자가 보이더라도 Static에 새로 구워진 것은 아니다.
4. Static 자체를 검사할 때에는 테스트 에셋의 폴백과 TMP Settings의 전역 폴백·기본 폰트가 대신 표시하는지도 살펴본다. 공용 설정을 바꿔 비교한다면 별도 실습 프로젝트에서 하고 변경값을 복원한다.
5. 문자 파일에 해당 글자를 추가하고 Static을 다시 생성한다. Character Table에 포함됐는지와 화면 표시를 함께 확인한다.

완료 기준은 **문자 파일의 갱신 → Static 재생성 → 주 폰트 포함 확인 → 화면 확인**이다. 폴백만 연결해서 보이게 만드는 것과 구분해 둔다.
