UV 작업에서 시간이 드는 곳은 펼치기 계산만이 아니다. 명령 찾기, 결과 확인, 다른 도구와 파일을 주고받는 과정도 반복된다. RizomUV 2027의 공식 발표는 이 흐름을 작업 공간 개선, 즉시 갱신, 스크립트 자동화로 연결한다.

*대표 이미지: RizomUV 공식 로고, 출처 Rizom-Lab의 Writing and Branding Guidelines. 로고 원본을 비율·색상 변경 없이 사용했으며, 공식 제휴나 후원을 의미하지 않는다.*

## 무슨 일이 있었나
{:.briefing-heading}

### 2027이라는 이름, 실제 제공 시작은 2026년 10월

Rizom-Lab의 공식 기능 페이지는 RizomUV 2027을 **2026년 10월 8일부터** Windows, macOS, Linux에서 제공한다고 안내한다. 제품명에 들어간 연도와 제공 시작 연도를 구분해야 한다. 페이지 본문에는 제공 시작일이 있지만, 별도의 게시 시각은 표시되지 않아 발표문 게시일로 단정하지 않는다.

이번 글은 제조사가 발표한 기능을 정리한다. 기존 버전 대비 실제 작업 속도나 파일 호환성을 독립 실험으로 확인한 리뷰는 아니다.

### 작업 공간과 UV 피드백을 함께 바꿨다

먼저 용어를 풀어 보면, **UV**는 3D 모델의 표면과 2D 텍스처의 위치를 연결하는 좌표다. 상자의 표면을 종이 전개도처럼 펼쳐 그 위에 그림을 배치한다고 생각하면 이해하기 쉽다. **UV 아일랜드**는 펼친 면들이 연결된 조각, **핀**은 수정 중 UV 위치를 붙잡아 두는 지정점이다. **텍셀 밀도**는 모델 표면의 일정 길이에 텍스처 픽셀이 얼마나 배정되는지를 뜻한다. 서로 다른 소품에서 이 비율이 크게 다르면 가까이 볼 때 선명도가 달라질 수 있다.

패널을 이동·분리하고 작업 공간을 프리셋으로 저장할 수 있다. 자주 쓰는 명령으로 도구 모음을 구성하고, Ctrl+K로 도구·설정·패널을 검색하는 기능도 소개됐다. Live Update는 엣지 제약을 추가하거나 제거할 때 해당 아일랜드를 즉시 다시 계산한다.

이 기능들의 연결점은 수정 결과를 확인하는 사이의 단계다. 예를 들어 펼치기와 검토에 서로 다른 작업 공간을 두고 제약을 바꾸며 결과를 볼 수 있다는 것이 공식 설명이다. 실제 사용 편의성은 작업자의 자산과 습관에 따라 확인해야 한다.

### 수동 작업을 재실행 가능한 스크립트로

공식 발표에 따르면 Python이 기본 스크립트 언어가 됐고, 명령 로그는 세션을 재실행 가능한 스크립트로 기록한다. 화면 없이 스크립트 기능을 사용하는 headless 모드도 추가됐다. 반복 처리와 제작 파이프라인 연결을 염두에 둔 변화다.

자동화 기능이 있다는 것과 모든 모델에 같은 규칙을 안전하게 적용할 수 있다는 것은 다르다. 예외 자산을 어떻게 처리할지는 팀의 검증 절차가 결정한다.

### 다른 도구로 돌아가도 UV 작업 상태를 남긴다

UV 제약, 핀, 브러시 맵, 대칭 평면을 FBX에 저장하는 기능과 glTF 2.0 가져오기·내보내기도 소개됐다. 텍스처 예산 측면에서는 앰비언트 오클루전을 이용해 밀도 맵을 채우는 기능을 안내한다. 덜 보이는 부분과 노출된 표면의 밀도를 다르게 배분하려는 접근이다.

파일 형식 지원만으로 모든 제작 도구와 완전한 왕복 호환이 보장되지는 않는다. 데이터를 남기는 기능과 다음 도구가 그 데이터를 보존하는지는 나누어 검사할 필요가 있다.

### 제작 작업은 어떻게 달라지나 — 나무 상자 소품 하나로 읽기

**다음은 기능을 이해하기 위한 가상 작업 예시이며, RizomUV를 실제로 실행한 기록이 아니다.** 3D 도구에서 만든 상자에 나무 텍스처를 입혀 게임 엔진으로 가져온다고 가정하자. 특정 도구 사이의 호환성이 보장된다는 뜻은 아니다.

| 작업 단계 | 확인하려는 것 | 이번 기능과의 연결 |
|---|---|---|
| 펼칠 위치를 정한다 | 상자 면의 연결을 어디서 나눌지 | 제약 수정과 Live Update로 결과를 확인하는 흐름 |
| UV 조각을 배치한다 | 면의 크기와 방향이 텍스처에 맞는지 | 작업별 패널 배치와 반복 명령 접근 |
| 변형된 상자에 반복한다 | 앞의 작업이 다른 형태에도 맞는지 | 명령 로그를 기록하고 재실행하는 흐름 |
| 다른 제작 도구를 거쳐 다시 연다 | UV와 추가 작업 상태가 남아 있는지 | FBX에 저장한 데이터의 실제 왕복 검증 |
| 엔진에서 본다 | 나무 무늬의 방향과 선명도가 괜찮은지 | 카메라 기준으로 텍스처 배분을 검토 |

이 예시에서 Live Update를 시험한다면 같은 상자에서 제약을 한 번 바꿔 보자. 바뀐 면이 어떻게 펼쳐졌는지, 수정 후 다시 확인하기까지 몇 단계가 필요한지 기록한다. 예상하지 않은 왜곡이 생기면 클릭 수가 줄어도 성공으로 세지 않는다.

명령 로그는 먼저 수동으로 괜찮은 결과를 만든 뒤 시험하는 편이 좋다. 복제 상자에 재실행하고, 길쭉한 상자처럼 형태가 다른 자산으로 범위를 넓힌다. 같은 명령이 실행됐다는 사실과 결과가 쓸 만하다는 판단을 나누어 기록한다. 이런 검사가 있어야 반복 작업의 자동화를 실제 제작에 넣을지 결정할 수 있다.

## 왜 중요한가
{:.briefing-heading}

**분석:** UV 도구의 가치는 계산 속도뿐 아니라 사람이 수정하고 확인하는 전체 과정에서 평가할 수 있다. 작업 상태가 보존되고 반복 명령을 재실행할 수 있다면, 수작업 노하우를 팀이 공유하는 절차로 옮길 여지가 생긴다. 다만 이는 기능에서 도출한 가능성이지, 이 글에서 측정한 생산성 향상은 아니다.

자동화는 잘못된 규칙도 빠르게 반복할 수 있다. 텍스처 밀도를 일괄 배분했을 때 눈에 잘 띄는 면이 충분히 선명한지, 작은 UV 조각에 여백이 남는지, 엔진에서 문제가 생기는지까지 보아야 한다. 새 기능을 도입하는 판단은 ‘몇 번 클릭을 줄였나’와 ‘품질 검토에 얼마나 시간을 썼나’를 함께 비교하는 편이 유용하다.

### 어떤 개발자에게 관련 있나

**필자의 판단:** 비슷한 소품을 여러 개 만들거나 UV 수정·파일 왕복을 반복하는 작업자에게 관련 있다. 코드·시나리오 작업이 대부분이고 3D 자산은 완성품을 가져다 쓰는 개발자라면 우선순위가 낮다. UV를 처음 배우는 단계라면 펼치기와 텍스처 배치의 기본 과정을 이해한 뒤 자동화를 시험하는 편이 좋다.

### 지금 도입할 만한가

**필자의 판단: UV 작업의 병목이 있을 때 소품 하나로 비교.** 기존 도구에서 불편한 단계가 무엇인지 먼저 적는다. 제약 수정이 잦다면 Live Update, 같은 조작을 반복한다면 명령 로그를 비교 대상으로 고른다. 발표된 기능 목록만으로 도구를 전면 교체하기보다 수정 시간과 결과 품질을 함께 확인한다. 실제 이용 요금과 계약 조건은 별도로 확인해야 한다.

## 개발에 적용할 점
{:.briefing-heading}

- **도구 변경을 검토한다면**, 자주 만드는 소품 하나를 기준 자산으로 정한다. 기존 방식과 새 방식의 펼치기·수정·검토 시간을 각각 기록하고 결과물 품질도 비교한다.
- **명령 로그를 자동화에 쓰려면**, 검증된 수동 작업 한 번을 기록해 복제 자산에 재실행한다. 다른 크기와 형태의 자산으로 넓혀 가며 실패 조건을 남긴다.
- **FBX 왕복을 쓴다면**, 핀과 제약을 지정한 테스트 파일을 내보내고 실제 사용하는 DCC를 거쳐 다시 연다. UV와 추가 데이터가 유지되는지 확인한 뒤 제작 규칙에 포함한다.
- **텍스처 예산을 재분배한다면**, 화면에서 가까이 보이는 면과 가려지는 면을 구분한다. 엔진의 목표 카메라·해상도로 비교하고, 밀도 변경이 필요한 면을 검토 목록으로 남긴다.
