여러 작업을 에이전트에게 맡기면 코딩뿐 아니라 결과 비교와 작업 공간 관리에도 시간이 든다. VS Code 1.141은 세션을 나란히 보는 화면과 비활성 worktree 정리를 소개한다. 여러 작업을 실제로 구분해서 쓰는 개발자에게 어떤 변화인지 살펴본다.

## 무슨 일이 있었나
{:.briefing-heading}

### 기능 — 세션 비교와 작업 공간 관리

Agents 창의 세션 격자는 대화를 가로·세로로 나누고 크기를 조절해 결과나 진행을 비교할 수 있게 한다. Worktree Cleanup은 비활성 세션의 공간 사용량을 보여주고 정리할 대상을 고르게 한다. 여기서 worktree는 같은 저장소의 별도 체크아웃으로 작업 파일을 분리하는 Git 기능이다.

공식 설명은 정리된 세션의 worktree를 나중에 다시 만들 수 있으며, 실행 중이거나 입력이 필요하거나 고정된 세션 등은 정리에서 보호한다고 안내한다. 이 설명만으로 모든 로컬 임시 파일이 보존된다고 가정하지 않는다.

### 조건 — 외부 세션 이어받기는 해당 환경에서

같은 기기의 외부 Copilot·Codex 세션을 Agents 창에서 이어 쓰는 흐름도 소개된다. 화면 분할은 병렬 작업의 생산성이나 변경 충돌 해결을 보장하는 기능이 아니다. 필요한 에이전트·계정·확장과 세션 조건을 자신의 환경에서 확인해야 한다.

## 왜 중요한가
{:.briefing-heading}

**분석:** 여러 결과를 비교할 때는 ‘창이 많다’보다 각 작업의 범위가 보이는지가 중요하다. 작업 공간을 정리할 때도 해당 세션이 정말 끝났는지와 필요한 산출물이 어디에 있는지를 먼저 확인해야 한다.

### 구체적인 작업 예시 — 구현과 검토를 나란히

**설명용 예시:** 작은 기능을 구현한 세션과 같은 변경을 검토한 세션을 나란히 둔다. 구현 쪽에서는 변경 파일·실행한 검사, 검토 쪽에서는 미확인 조건·수정 제안을 읽는다. 서로 다른 파일 범위를 혼동하거나 다른 커밋을 검토했다면 비교를 멈추고 기준을 맞춘다.

디스크 공간 점검은 이후 별도 단계로 둔다. 보관할 결과 파일과 PR 상태를 확인하고, 종료된 시험 작업 하나에서 복구 절차를 먼저 이해한다. 이 글에서는 실제 작업 공간을 삭제하지 않았다.

### 어떤 개발자에게 관련 있나 · 지금 도입할 만한가

**필자의 판단:** VS Code에서 여러 세션과 작업 공간을 쓰는 개발자에게 관련 있다. 하나의 대화만 쓰면 효과가 작을 수 있다. 먼저 비교 화면을 시험하고, 자동 정리는 자신의 보관 조건을 이해한 뒤 검토하는 편이 좋다.

## 개발에 적용할 점
{:.briefing-heading}

- 나란히 비교할 두 세션의 저장소·브랜치·커밋을 먼저 맞춘다.

- 작업 공간 크기와 보관할 산출물 위치를 확인한 뒤 정리 대상을 고른다.

- 정리와 복구는 중요한 작업보다 종료된 시험 작업에서 먼저 확인한다.
