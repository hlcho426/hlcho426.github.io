> 유니티 C# 공부 중에 "유니티의 1은 1미터"라는 말을 보고 궁금해진 것을 Claude(AI)에게 물어보고, 그 답을 Claude가 정리한 글이다.
{: .prompt-info }

[기초 Day 5](/posts/csharp-week-basic-day5/)를 공부하다가 "유니티의 1은 1미터로 생각한다. 중력도 이 기준에 맞춰져 있다"는 문장에서 멈췄다. 그럼 캐릭터 모델링도, 배경도, 소품도 처음부터 크기가 다 맞아야 한다는 뜻 아닌가?

퇴사하기 전 회사에서 게임을 만들 때, 게임의 캐릭터들과 메인 오브젝트들의 크기가 달랐다. 캐릭터보다 메인 프랍이 몇십 배 컸다. 그래서 카메라도 따로 썼다. 캐릭터가 프랍과 함께 나와야 할 때는 어쩔 수 없이 둘 중 하나의 크기를 조정했다. 그때는 그러자고 하니 그래야 하는 줄 알았는데, 그 뒤로 스케일 이슈가 계속 터졌다. 그래서 궁금했다. 무엇이 정석인지.

## 1. 유니티의 1은 1미터
{:.briefing-heading}

유니티가 "1 = 1미터"를 강제하지는 않는다. 숫자 1이 1cm여도, 1km여도 화면은 그려진다. 하지만 유니티의 물리는 1을 1미터로 보고 맞춰져 있다.

- 중력 기본값이 (0, -9.81, 0)이다. 지구 중력 9.81m/s²를 그대로 쓴다.
- Rigidbody의 질량 기본값 1은 1kg이다.
- 충돌 계산에 쓰는 여유 거리(Default Contact Offset) 같은 기본값도 손바닥에서 건물 크기쯤의 물체에 맞춰져 있다.

유니티가 만들어 주는 기본 도형도 이 기준이다. 크기를 잴 때 자로 쓰기 좋다.

| 기본 도형 | 크기 |
|---|---|
| Cube | 한 변 1m |
| Capsule | 키 2m, 지름 1m |
| Plane | 가로세로 10m |
| Character Controller (기본값) | 키 2m, 반지름 0.5m |

그래서 처음부터 **1 = 1미터로 정하고 모든 걸 현실 크기로 만드는 것**이 제일 편하다. 현실이 이미 "서로 잘 맞는 크기표"라서 따르기만 하면 캐릭터와 배경이 자연스럽게 맞는다.

## 2. 크기가 왜 '느낌'을 바꿀까
{:.briefing-heading}

물체가 떨어지는 시간은 떨어지는 높이와 중력으로 정해진다(시간 = √(2 × 높이 ÷ 중력)). 크기만 다른 공 두 개를 같은 중력에서 떨어뜨려 보자. 둘 다 자기 키의 두 배 높이에서 떨어진다.

| 공 크기 | 떨어지는 높이 | 걸리는 시간 |
|---|---|---|
| 지름 7cm | 14cm | 약 0.17초 |
| 크게 만든 1m | 2m | 약 0.64초 |

화면에서는 똑같은 공이 똑같이 자기 키의 두 배만큼 떨어지는데, 큰 쪽은 네 배 가까이 느리다. 그래서 "둥둥 떠서 떨어지는" 느낌이 난다. 거인이 사는 세상을 보는 셈이다.

여기서 규칙 하나가 나온다. **세상을 k배 크게 만들었다면 중력도 k배 세게 해야 원래 느낌이 난다.** 이동 속도, 점프 힘처럼 거리와 관련된 값도 함께 k배가 된다. 그러니 물체를 일부러 크게 만드는 것 자체가 잘못은 아니다. 그만큼 중력과 속도를 같이 맞추면 된다.

문제는 그걸 **처음에 정하지 않고 그때그때 맞춰 가는 것**이다. 프랍은 크게, 캐릭터는 다른 크기로 만들어 두고 둘을 한 화면에 세울 때마다 한쪽 크기를 바꾸기 시작하면, 중력도 점프도 카메라도 어느 쪽 기준에 맞출지 매번 다시 정해야 한다. 스케일 문제가 계속 터지는 이유가 이것이다.

## 3. 처음에 정하는 것: 스케일 가이드
{:.briefing-heading}

프로젝트를 시작할 때 아래 네 가지를 정하고, 그다음부터는 바꾸지 않는다.

1. **자 하나**: 1 = 1미터.
2. **크기표**: 주요 물체의 크기를 표로 적어 아트 작업자와 공유한다. 기획 문서에 한 장 넣으면 된다.
3. **Scale은 (1, 1, 1)**: 크기가 안 맞으면 씬에서 Transform의 Scale을 늘려 맞추지 않는다. 모델링 툴이나 유니티의 모델 Import 설정에서 고친다. 씬에서 Scale로 맞추기 시작하면 자식 오브젝트, 물리, 애니메이션이 줄줄이 꼬인다.
4. **회색 상자로 먼저 (그레이박스)**: 아트를 만들기 전에 큐브와 캡슐만으로 레벨을 짜서 점프 높이, 문 크기, 카메라 거리를 먼저 맞춘다. 아트는 그 크기에 맞춰 만든다.

크기표는 현실 크기에서 시작한다.

| 물체 | 현실 크기 (대략) |
|---|---|
| 성인 키 | 1.6~1.8m |
| 방문 | 높이 2.1m, 폭 0.9m |
| 천장 높이 (아파트) | 2.3~2.4m |
| 계단 한 칸 | 높이 0.15~0.2m |
| 식탁 | 높이 0.72~0.75m |
| 의자 앉는 면 | 높이 0.43~0.45m |
| 머그컵 | 높이 약 0.1m |
| 탁구공 | 지름 0.04m |

게임은 여기서 일부러 과장하기도 한다. 3인칭 게임은 카메라가 캐릭터 뒤를 따라다녀서 문과 통로를 현실보다 넓고 높게 만드는 경우가 많다. 이런 과장도 "문은 현실의 1.3배"처럼 크기표에 같이 적어 둔다. 과장이 규칙이 되면 일관성은 그대로 지켜진다.

## 4. 크기가 맞는지 확인하는 법
{:.briefing-heading}

**기준 자를 씬에 세워 둔다.** 사람 키만 한 캡슐(유니티 기본 캡슐은 2m)이나 1m 큐브를 프리팹으로 만들어 두고, 새 모델을 가져올 때마다 옆에 세워서 비교한다.

**모델링 툴도 같은 자를 쓴다.** 블렌더는 기본이 1 = 1미터라 그대로 만들면 된다. FBX로 내보낼 때 스케일 옵션을 확인하고, 유니티로 가져온 뒤 Scale이 (1, 1, 1)인 상태에서 기준 캡슐 옆에 세워 크기가 맞으면 통과다. 100배 크거나 작게 들어오는 일이 흔한데, 이 단계에서 잡아 두면 나중에 고생하지 않는다. 유니티 쪽에서는 모델 Import 설정의 **Scale Factor**와 **Convert Units**로 고칠 수 있다.

**2D라면 Pixels Per Unit을 통일한다.** 2D에서 이 역할을 하는 게 스프라이트의 **Pixels Per Unit(PPU)**이다. 기본값 100이면 100픽셀이 1m다. 캐릭터 그림이 160픽셀이면 1.6m가 된다. 스프라이트마다 PPU가 다르면 같은 크기로 그려도 게임 안에서 크기가 달라지니, 프로젝트 전체에서 하나로 통일한다. 2D 물리의 중력도 기본이 9.81이라 같은 이야기가 적용된다.

## 5. 크기는 처음에, 느낌은 나중에
{:.briefing-heading}

크기가 일관되게 맞춰졌다면, 그다음의 중력·점프·속도 조절은 **보정이 아니라 연출**이다. 이 둘을 섞지 않는 게 핵심이다.

현실 중력은 게임에서 오히려 둥둥 뜨는 느낌이 나는 경우가 많다. 그래서 많은 게임이 중력을 2~3배로 올리거나, 떨어질 때만 더 세게 당긴다. 전체 중력은 **Project Settings → Physics → Gravity**에서 바꾸고, 특정 캐릭터만 바꾸고 싶으면 코드로 힘을 더한다.

```csharp
using UnityEngine;

public class BetterFall : MonoBehaviour
{
    [SerializeField] float fallMultiplier = 2f;   // 떨어질 때 중력 배수
    Rigidbody rb;

    void Awake()
    {
        rb = GetComponent<Rigidbody>();
    }

    void FixedUpdate()
    {
        // 내려가는 중이면 중력을 (배수 - 1)만큼 더 준다
        if (rb.linearVelocity.y < 0f)
            rb.AddForce(Physics.gravity * (fallMultiplier - 1f), ForceMode.Acceleration);
    }
}
```

`fallMultiplier`를 `[SerializeField]`로 꺼내 두면, 플레이하면서 Inspector에서 숫자를 바꿔 손맛을 맞출 수 있다. 크기는 고정해 두고 이런 수치만 만지는 것이다. (`linearVelocity`는 Unity 6의 이름이다. 그 전 버전에서는 `velocity`다.)

## 6. 작은 세상과 큰 세상의 함정
{:.briefing-heading}

테이블 위처럼 작은 물체를 가까이서 보는 게임은 이것부터 확인한다.

- **카메라가 가까운 물체를 잘라 먹는다.** 카메라의 Near Clipping Plane 기본값이 0.3m라서, 실제 크기의 작은 소품을 가까이서 찍으면 30cm보다 가까운 부분이 잘려 보인다. 테이블 위 게임이면 0.01~0.05로 줄인다.
- **작고 빠른 물체는 벽을 뚫고 지나갈 수 있다.** 한 번 계산하는 사이에 벽을 통째로 넘어가 버려서다. Rigidbody의 Collision Detection을 Continuous로 바꾼다.

반대로 세상을 크게 만들 때도 함정이 있다.

- 2번에서 본 것처럼 떨어지는 게 느려 보인다. 중력과 속도를 함께 올려야 한다.
- 원점에서 수 km 이상 멀어지면 소수점 정밀도가 떨어져서 물체가 덜덜 떨린다. 거대한 오픈 월드가 아니면 잘 만날 일은 없지만, 세상을 10배로 키우면 그만큼 빨리 만난다.

## 정리
{:.briefing-heading}

- 유니티는 1을 1미터로 보고 물리가 맞춰져 있다. 처음부터 1 = 1미터, 현실 크기로 만든다
- 세상을 k배 크게 만들면 중력과 속도도 k배여야 같은 느낌이 난다. 그래서 크기는 처음에 한 번 정한다
- 크기표(스케일 가이드)를 문서로 남기고, 과장도 규칙으로 적는다
- Transform의 Scale은 (1, 1, 1). 크기는 모델링 툴이나 Import 설정에서 맞춘다
- 기준 캡슐을 씬에 세워 두고, 회색 상자로 먼저 레벨을 짠다. 2D는 PPU를 통일한다
- 크기는 처음에, 손맛(중력·점프·속도)은 나중에 Inspector 수치로 조절한다
